## 1. 連線架構：分區式輕量 MMO（不做真正 Persistent World）

### 問題
原始 GDD 通篇講「MMORPG」，但完全沒有講清楚「玩家怎麼互相看見彼此」這件事要怎麼實作。
這是 MMO 跟單機/自走棋最本質的差異：持久共享世界需要伺服器權威架構 + 24/7 維運成本，
對個人開發者幾乎不可行。

### 決策
採用**「分區式輕量 MMO」**，不做真正數千人同螢幕的 Persistent World：

```
                    ┌─────────────┐
                    │   帳號伺服器   │
                    └──────┬──────┘
                           │
             ┌─────────────┴─────────────┐
             │                           │
        【玩家資料】                  【社交資料】
        角色/背包/裝備                 好友/公會
             │                           │
             └─────────────┬─────────────┘
                           │
                    【世界服務】
                           │
         ┌─────────────────┼─────────────────┐
         │                 │                 │
      青嵐城-01           青嵐城-02          青嵐城-03
      50~100人            50~100人           50~100人
         │                 │                 │
         └────────────┬────┴────────────┘
                      │
                 【副本服務】
                      │
             ┌────────┼────────┐
             │        │        │
          1~4人     5~10人   10~20人
           Instance  Instance  Instance
```

具體規則：

| 區域類型 | 共享方式 |
|---|---|
| 城市（青嵐城） | 分流，每分區 50～100人，玩家可見彼此、擺攤、聊天 |
| 野外（青嵐古林等） | 半共享，單張地圖 20～40人上限，超過開新分流 |
| 副本 | 完全 Instance（1隊玩家一個房間，結束即關閉） |
| 世界事件/世界BOSS | 「共享事件 Instance」——同一事件開多個頻道（Channel 01/02/03…），每頻道 50～100人，玩家仍會感覺「全世界都在打這隻」，但技術成本遠低於真正的全服共享 |

### 為什麼不是「真 MMO」也不是「偽 MMO」
- 「真 MMO」（單一持久共享世界，數千人同地圖）：個人開發者不可行，直接排除。
- 「偽 MMO」：早期 Claude 用這個詞描述同一套架構，但這個講法容易讓人誤解成
  「隨便做個多人聊天室加減看看」，低估了工程量，故棄用此詞。
- 「分區式輕量 MMO」：跟上面兩者的技術骨架相同（大廳共享 + instance 副本 + 世界事件
  頻道化），但明確傳達「玩家體感像 MMO，工程規模可控」，是本專案採用的正式名稱。

### ⚠️ 工程風險提醒（別被「輕量」誤導）
即使是這套「輕量」架構，仍然需要：
- **伺服器端戰鬥模擬**：只要戰鬥機制涉及玩家閃避/走位判定（見第 3 節），
  判定就不能只信任 client，否則等於送出一個「宣稱自己有閃就不會被打」的外掛漏洞。
  這代表「伺服器權威即時戰鬥模擬」不是可選項，是機制型戰鬥設計成立的前提。
- **Interest Management**：50~100人同分區時，不能無腦把所有人的位置/動作廣播給
  所有人，否則頻寬與client效能會直接爆掉，需要「只同步玩家視野範圍內物件」這類
  MMO工程裡出了名難的優化技巧。
- **跨分區玩家資料一致性**：玩家從城-01移動到城-02、或進出副本時，帳號資料的讀寫
  時機需要仔細設計，避免競態條件（race condition）造成道具/貨幣複製或遺失。

這些都是數月起跳的工程量，不是「找個 managed game-server SDK 接上去就好」。

### 技術棧：待拍板（下一步最優先事項）
候選方案（尚未選定）：
1. **Photon Fusion**：托管、商業授權，上手快，但有流量計費
2. **Unity Netcode for GameObjects + Relay**：Unity官方方案，免費額度但功能較陽春
3. **自建 Node.js/Colyseus 後端**：彈性最高，但等於自己維運 server，對個人開發者是最重的選項

**下一步行動**：在開始寫 Vertical Slice 的多人程式碼之前，必須先選定其中一條路線並寫一版
`17_TECH_ARCHITECTURE.md` / `18_NETWORK_ARCHITECTURE.md` 驗證雛形（至少要跑通「兩個client
在同一個instance房間裡看到彼此移動」這個最小案例）。

## 2. 裝備 vs 靈印：明確數值分工

### 問題
原始GDD中，裝備（萬兵閣鍛造）跟靈印（8槽）都被描述成「強化Build」，玩家會分不清楚
「這兩套系統為什麼都要練」。

### 決策

| 系統 | 負責什麼 | 不負責什麼 |
|---|---|---|
| **裝備** | 角色底層數值：攻擊、防禦、生命、暴擊、攻速、屬性抗性 | 不改變技能規則、不改變戰鬥打法 |
| **靈印** | 戰鬥規則與Build玩法：改變技能觸發條件、追加特殊效果 | 不是單純 `+500攻擊` 這種裸數值 |

一句話定調：**「裝備決定你有多強，靈印決定你怎麼戰鬥。」**

靈印範例修正方向（取代原本的裸數值式範例）：
- 赤炎：第三次技能命中後燃燒敵人
- 玄甲：受到致命傷害時生成護盾
- 影遁：閃避後進入短暫隱身
- 雷鳴：連續攻擊同一目標時召喚雷擊
- 幻月：控制技能命中後，使敵人受到幻術干擾

靈印應該被設計成「Build核心」，讓玩家組合出風格化的流派，例如：
- Build A「火焰爆發」：赤炎 + 赤炎 + 雷鳴 + 暴炎 + 灼魂
- Build B「閃避刺殺」：影遁 + 疾風 + 暗殺 + 幻影 + 瞬殺
- Build C「坦克反傷」：玄甲 + 磐石 + 反震 + 護魂 + 不屈

**待補**：完整靈印資料表（見 `04_SPIRIT_SEAL_SYSTEM.md`，尚未建立）。

## 3. 戰力設計：戰力決定容錯率，機制決定上限

### 問題
原始GDD只寫了一句設計口號「戰力不能決定一切」，沒有任何機制支撐，等於空話。

### 決策
改寫為可執行的設計條款：

> **「戰力決定容錯率，機制決定上限。」**
> 高戰力玩家操作失誤時容錯空間較大；低戰力玩家操作精準時，
> 可以透過機制設計贏過戰力更高但操作較差的對手。

至少要有 5 種「低戰勝高戰」機制類型，之後每個副本/BOSS至少要用到其中一種：

1. **屬性克制**：例如 火→木→雷→水→火 的循環克制，而非單純比戰力數字
2. **BOSS機制**：例如 BOSS有護盾，硬打只有10%傷害，必須先打掉四個符文柱才能破盾
3. **走位機制**：地面出現警示圈（如雷擊/範圍傷害），不閃就會被秒殺，跟戰力無關
4. **靈印Counter**：特定靈印組合可以克制特定敵人套路（見第2節的Build範例）
5. **操作深度**：雙武器切換的時機判斷（例如BOSS蓄力時切遠程武器風箏、硬直時切近戰爆發）

設計哲學參考（不是要照抄，是借鑑設計思路）：
- 《原神》：元素反應機制讓純數值以外的配置與操作有價值
- 《Monster Hunter》：裝備與玩家技術不完全等價，敵人招式/位置/時機非常重要
- MOBA類：經濟/裝備優勢不等於100%必勝，機制優勢可以彌補部分數值劣勢

### ⚠️ 與第1節的連動
這裡所有「走位/閃避/機制判定」要成立，前提是伺服器端能驗證玩家的實際位置與動作，
不能只信任client端回報。**這代表本節的機制設計，跟第1節的「伺服器權威即時戰鬥模擬」
是同一塊工程，不是各自獨立的進度**，GDD後續文件應把兩者放在一起追蹤，避免有人誤以為
「機制設計」跟「伺服器架構」可以分開排期。

## 4. 商業化：第一階段不做抽卡，走 Battle Pass + 外觀 + 月卡

### 問題
原始GDD完全沒有商業化設計。對於「個人+AI輔助開發、目標上架」的規模，
這是除了連線架構外第二大的缺口——如果先把所有養成系統設計好才回頭想「商城賣什麼」，
屆時要嘛破壞已建立的平衡（戰力不能決定一切），要嘛要大改已完成的系統。

### 決策

**第一階段主力變現**：
- **月卡**（「修行月令」）：每日資源、額外任務、每日體力、外觀、掃蕩次數、少量便利性
- **Battle Pass**（「天玄試煉季」）：完成每日/每週任務、探索、副本、世界BOSS取得通行證
  經驗，獎勵為外觀/坐騎/表情/家具/名稱框/特效等非戰力道具
- **外觀商城**：時裝、武器外觀、翅膀、坐騎、寵物外觀、技能特效、城市稱號、名片、宿舍家具

**第一階段刻意不做**：
- 角色/靈印/裝備抽卡（保底、機率、重複轉換、星級突破——複雜度對個人開發規模過高，
  且容易一開始就踩到「玩家開發者工具偵測到機率造假」這類信任風險）
- **戰力直購**（任何形式的 `+X%攻擊` 販售）——一旦開了這個口子，第3節建立的
  「戰力不能決定一切」設計原則直接崩掉，是絕對禁區
- 強制廣告（沉浸感優先的MMORPG不適合「擊殺世界BOSS→看廣告復活」這種廉價體驗；
  可以考慮非強制的 Rewarded Ads，例如「看廣告換一次額外採集」，但不作為主要收入來源）

### 合規提醒（跟萌戰三國專案踩過的坑一致）
一旦有儲值機制，需要注意：
- 台灣法規：依法需辦理「遊戲軟體分級」，跟是否上架App Store無關
- 不能用Apple/Google內購（抽15~30%）的話，需自接第三方金流（綠界/藍新/TapPay等），
  需要商業登記/公司行號才能合法收款開發票
- **金流驗證必須放伺服器端**，不能由client端判斷「已購買」——這點會影響第1節的
  帳號伺服器設計，購買紀錄與道具持有需要伺服器權威驗證

## 5. 戰鬥操作深度：三層自動化，不是二選一

### 問題
原始GDD同時寫了「自動戰鬥」跟「雙武器路徑即時切換」，兩者服務的受眾看似衝突
（硬核操作 vs 輕度掛機），需要先決定核心受眾。

### 決策
不二選一，改採**三層戰鬥自動化**，讓不同玩家群都能找到自己的舒適區：

| 內容類型 | 自動化程度 |
|---|---|
| 普通野外 / 採集 / 低階副本 / 日常任務 | 全自動（點一下，角色自己打） |
| 中階副本 | 半自動（玩家控制移動、雙武器切換、大招；普攻與部分技能自動） |
| 高階秘境 / 世界BOSS / PVP / 排位 | 手動為主，弱化或禁用自動 |

核心戰鬥定位：**「平時很輕，關鍵時刻很深。」**——不是《原神》那麼硬核，也不是純放置類
那麼輕，適合手機碎片時間 + 保留操作深度的雙軌需求。

半自動模式下的具體操作範例（雙武器切換的意義）：
```
BOSS蓄力 → 玩家切弓 → 後撤 → BOSS技能落空
        → 遠程輸出 → BOSS進入硬直 → 切劍 → 近戰爆發 → 觸發靈印Combo
```
自動模式下 AI 只會固定輪替「普攻→技能→普攻→技能」，效率明顯低於手動的時機判斷，
藉此讓玩家真的感受到「操作得好，效率比自動更高」。

## 6. 修訂後的五條設計原則（取代原GDD第14/38章對應段落的表述）

| 原則 | 原GDD表述 | 修訂後表述 |
|---|---|---|
| 一 | MMORPG | 分區式輕量 MMO：帳號持久化 + 城市多人分區 + 野外半共享 + 副本Instance + 世界事件頻道化，不做真正持久共享大地圖 |
| 二 | 裝備+靈印都負責Build | 裝備＝數值成長，靈印＝戰鬥Build規則，兩者互補不重複 |
| 三 | 戰力不能決定一切 | 戰力決定容錯率，機制決定上限 |
| 四 | 尚未規劃商業化 | 第一階段：Battle Pass + 外觀商城 + 月卡；絕對禁區：戰力直購、強制廣告、開局複雜抽卡 |
| 五 | 自動戰鬥 + 手動戰鬥 | 三層自動化：日常全自動、中階半自動、高階/PVP手動為主 |
